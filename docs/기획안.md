# DemoDay 기획안 — 레포로 만드는 발표용 데모 영상

Nov 22, 2026 · @정덕환

## 서비스 개요

DemoDay는 GitHub 레포 링크와 배포 URL만 넣으면, 실제 화면과 코드 구조를 바탕으로 발표용 데모 모션그래픽 영상을 만들어주는 컴퓨터학부생 전용 서비스다.

- **한 줄 소개:** "시연을 찍지 마세요, 레포를 넣으세요."
- **서비스명:** DemoDay.
- **핵심 가치:** 프롬프트를 설명할 필요 없이 코드에서 흐름을 뽑고, 실제 화면을 쓰기 때문에 "가짜 데모"가 아닌 영상을 만든다.

범용 AI 영상 도구와의 차이는 입력이 프롬프트가 아니라 코드라는 점, 그리고 결과물이 영상이 아니라 발표라는 점이다.

## 문제 정의

컴퓨터학부생은 결과물을 만드는 데는 익숙하지만, 그것을 보여주는 영상을 만드는 데는 시간과 기술이 부족하다.

- **반복되는 수요:** 캡스톤, 해커톤, 공모전, 포트폴리오, 인턴 지원까지 데모영상이 필요한 순간이 학기마다 생긴다.
- **시연 촬영의 어려움:** 마감 직전에 버그가 나거나, 서버가 불안정하거나, 화면 녹화가 지저분해서 몇 번씩 다시 찍게 된다.
- **편집 역량 부족:** 줌, 커서 강조, 전환 효과 같은 모션 편집은 대부분 개발자의 전문 영역이 아니다.
- **범용 AI의 한계:** 프롬프트로 영상을 만들면 실제 서비스와 다른 화면이 나오고, 일부만 고치기 어렵고, 아키텍처 같은 개발 맥락을 잘 표현하지 못한다.
- **심사 관점의 문제:** 실제 화면과 동떨어진 모션그래픽은 "가짜 데모"로 보여 오히려 신뢰를 떨어뜨린다.

## 타깃 사용자와 사용 상황

주 타깃은 웹 서비스 프로젝트를 발표해야 하는 컴퓨터학부 학부생 팀이다.

| 사용자 | 상황 | 원하는 결과 |
| --- | --- | --- |
| 캡스톤·종합설계 팀 | 최종 발표 전 데모영상 제출 | 핵심 기능 흐름 + 아키텍처 설명 영상 |
| 해커톤 참가 팀 | 마감 직전, 기능이 일부만 완성됨 | 실제 동작하는 부분 중심의 짧은 데모 |
| 개인 포트폴리오 준비생 | 인턴·취업 지원용 프로젝트 소개 | README나 이력서에 넣을 1분 영상 |
| 수업 팀 프로젝트 | 학기말 발표, 시간 제한 있음 | 발표 시간에 맞춘 데모 구간 |

MVP 단계에서는 웹 프론트엔드가 있는 프로젝트(React, Vue, Next.js 등)로 범위를 한정한다. 모바일 앱이나 CLI 도구는 확장 단계에서 다룬다.

## 기존 대안과 차별점

기존 도구는 "무엇을 보여줄지"를 사용자가 정해야 하지만, DemoDay는 코드에서 그것을 찾아낸다.

| 구분 | 입력 | 실제 화면 사용 | 개발 맥락(아키텍처 등) | 부분 수정 | 발표 맞춤 |
| --- | --- | --- | --- | --- | --- |
| 범용 AI (프롬프트 → 애니메이션 코드) | 텍스트 설명 | 어려움 | 직접 설명해야 함 | 어려움 | 없음 |
| 화면 녹화·편집 툴 | 직접 녹화 | 가능 | 없음 | 가능 | 일부 |
| 템플릿형 모션 툴 | 수작업 편집 | 직접 넣어야 함 | 없음 | 가능 | 없음 |
| **DemoDay** | **레포 + 배포 URL** | **자동 캡처** | **코드에서 자동 추출** | **장면 단위** | **시간·대본 맞춤** |

차별점은 다섯 가지로 정리한다.

1. **코드 기반 흐름 추출:** 라우트와 컴포넌트를 분석해 "로그인 → 메인 → 핵심 기능" 같은 시연 시나리오를 자동으로 만든다.
2. **실제 화면 기반:** 헤드리스 브라우저로 실제 서비스를 조작하며 캡처하므로 가짜 데모 비판을 피한다.
3. **개발자 발표 전용 장면:** 아키텍처, API 요청 흐름, ERD를 코드에서 뽑아 애니메이션으로 만든다.
4. **발표 맥락 출력:** 발표 시간 제한, 대본 싱크, 슬라이드 삽입용 형식을 지원한다.
5. **장면 단위 수정:** 전체를 다시 만들지 않고 "이 장면만 느리게", "이 버튼 강조"처럼 고칠 수 있다.

경쟁 서비스 현황은 빠르게 바뀌므로, 발표 전에 최신 도구를 한 번 직접 조사해 표를 갱신한다.

## 핵심 기능 상세

핵심 기능은 레포 분석, 화면 캡처, 장면 생성, 개발 맥락 애니메이션, 편집·내보내기의 다섯 단계로 구성된다.

### 1. 레포 분석과 시나리오 추출

- 라우터 설정(React Router, Next.js pages/app 디렉터리 등)에서 페이지 목록을 뽑는다.
- 페이지별 주요 컴포넌트와 버튼·폼을 파악하고, README에서 서비스 설명과 핵심 기능을 읽는다.
- LLM이 이를 바탕으로 "보여줄 순서"를 담은 시나리오(장면 목록)를 제안하고, 사용자가 순서를 바꾸거나 장면을 뺄 수 있다.

### 2. 실제 화면 자동 캡처

- 시나리오대로 헤드리스 브라우저가 배포 URL에 접속해 클릭, 입력, 스크롤을 수행한다.
- 각 단계의 스크린샷과 클릭 좌표, 화면 전환 시점을 기록한다.
- 로그인이 필요한 서비스는 테스트 계정을 입력받는다.

### 3. 모션그래픽 장면 생성

- 캡처한 실제 화면 위에 줌 인, 커서 이동, 클릭 하이라이트, 자막, 장면 전환을 입힌다.
- 장면 구성은 JSON으로 표현하고, 영상 렌더러가 이를 그대로 그린다.
- 색상과 폰트는 프로젝트 화면에서 추출해 영상 톤을 서비스와 맞춘다.

### 4. 개발 맥락 애니메이션

- 패키지 설정과 폴더 구조로 기술 스택과 아키텍처 다이어그램을 만든다.
- API 호출 코드를 따라 "프론트 → 백엔드 → DB → 응답" 요청 흐름을 애니메이션으로 보여준다.
- 모델·엔티티 정의가 있으면 ERD 장면을 만든다.

### 5. 편집과 내보내기

- 장면별로 길이, 자막, 강조 위치를 수정하고 자연어로 수정 요청도 할 수 있다.
- 전체 길이를 발표 시간(예: 60초, 90초, 3분)에 맞춰 자동 조정한다.
- MP4로 내보내고, 슬라이드 삽입용 짧은 클립과 GIF도 제공한다.

## 사용자 흐름

사용자는 링크 두 개와 몇 번의 확인만으로 영상을 받는다.

1. GitHub 레포 링크와 배포 URL을 입력한다. 필요하면 테스트 계정과 발표 시간(60초, 90초, 3분)을 함께 입력한다.
2. 서비스가 레포를 분석해 시연 시나리오 초안(장면 목록)을 보여준다.
3. 사용자가 장면 순서를 바꾸거나 빼고, 아키텍처·요청 흐름 장면 포함 여부를 고른다.
4. 헤드리스 브라우저가 시나리오대로 실제 화면을 캡처한다.
5. 캡처 화면에 모션을 입힌 미리보기 영상이 나온다.
6. 장면별로 수정한다. 만족할 때까지 5번과 6번을 반복한다.
7. MP4, 슬라이드용 클립, GIF 중 원하는 형식으로 내려받는다.

코드 분석과 실제 화면 캡처, 두 갈래의 결과가 LLM 장면 구성 단계에서 합쳐져 하나의 영상이 된다.

위쪽 줄은 데모 흐름, 가운데 왼쪽은 개발 맥락 장면을 만들고, 둘 다 장면 구성으로 모인다. 사용자의 수정 요청은 장면 구성으로 돌아가 다시 렌더링된다.

| 영역 | 기술 후보 | 역할 |
| --- | --- | --- |
| 웹 프론트엔드 | Next.js | 입력, 시나리오 확인, 미리보기·편집 UI |
| 백엔드 | FastAPI 또는 Spring Boot | 작업 관리, 분석·캡처·렌더링 호출 |
| 레포 분석 | GitHub API + 파일 파서 | 라우트, 컴포넌트, README, package.json 수집 |
| LLM | Claude API 등 | 시나리오 생성, 장면 JSON 생성, 아키텍처 요약 |
| 화면 캡처 | Playwright | 시나리오대로 클릭·입력하며 스크린샷과 좌표 기록 |
| 영상 렌더링 | Remotion | 장면 JSON을 React 컴포넌트로 그려 MP4 출력 |
| 작업 큐·저장소 | Redis 큐 + 오브젝트 스토리지 | 오래 걸리는 렌더링 비동기 처리, 결과물 저장 |

핵심 설계는 LLM이 영상을 직접 만들지 않고 장면 JSON만 만든다는 점이다. 그래서 결과가 일관되고, 장면 단위 수정이 쉽다.

## 해커톤 MVP 범위와 일정

MVP는 "레포 + URL 입력 → 실제 화면 기반 데모 영상 + 아키텍처 장면 1개"까지를 목표로 한다.

| 기능 | MVP 포함 | 구현 수준 |
| --- | --- | --- |
| 레포 분석 → 시나리오 추출 | 포함 | React/Next.js 라우트 + README만 분석 |
| 실제 화면 자동 캡처 | 포함 | 시나리오 5\~7단계, 로그인 없는 페이지 우선 |
| 모션 장면 생성 | 포함 | 줌, 커서, 클릭 강조, 자막, 전환 4\~5종 템플릿 |
| 아키텍처 애니메이션 | 포함 | package.json·폴더 구조 기반 다이어그램 1장면 |
| 요청 흐름·ERD 애니메이션 | 제외 | 발표에서 향후 계획으로 언급 |
| 장면 단위 수정 | 일부 | 장면 순서·길이·자막 수정만 |
| 발표 시간 맞춤 | 포함 | 장면 길이 비율로 자동 조정 |
| 자연어 수정 요청 | 제외 | 향후 계획 |

### 3인 분업 계획 (11/24 정오 제출)

제출까지 약 1.5일이므로, 첫 회의에서 JSON 형식만 맞추고 세 명이 따로 개발한 뒤 11/23 저녁에 한 번 합친다. 서로를 기다리지 않도록 B와 C는 하드코딩한 JSON으로 먼저 개발한다.

**2일 일정에 맞춘 범위 조정**

- 아키텍처 장면은 차별점의 핵심이라 package.json 기반 1장면으로 유지한다.
- 장면 수정은 순서·길이·자막만 웹에서 고치는 수준으로 줄인다.
- 로그인이 필요한 페이지는 제외하고, 캡처 실패 시 스크린샷을 직접 올리는 폴백만 둔다.
- 렌더링은 Remotion을 로컬에서 실행하고, 작업 큐와 스토리지는 생략한다.

**역할**

| 담당 | 맡는 일 | 최종 산출물 |
| --- | --- | --- |
| A · 분석·LLM·백엔드 | GitHub API로 라우트·README 수집, 시나리오·장면 JSON 생성 프롬프트, FastAPI로 분석 → 캡처 → 생성 → 렌더 호출 연결 | 분석·생성 API, scenario.json, scene.json |
| B · 캡처·렌더링 | Playwright 캡처 스크립트, Remotion 타이틀·화면(줌·커서·자막)·전환 템플릿, 렌더 스크립트와 발표 시간 맞춤 | capture.json과 스크린샷, scene.json을 MP4로 만드는 스크립트 |
| C · 프론트·아키텍처 장면 | Next.js 입력·시나리오 확인·미리보기·장면 수정 화면, package.json·폴더 구조에서 아키텍처 노드·연결 추출, Remotion 아키텍처 장면 템플릿, 샘플 레포 2개 준비와 테스트 | 웹 UI, 아키텍처 추출 모듈, 아키텍처 장면 컴포넌트 |

**인터페이스 약속 (첫 회의에서 확정)**

scenario.json — A가 만들어 B에게 넘긴다.

```json
{"baseUrl": "https://sample.vercel.app", "steps": [
  {"id": 1, "action": "goto", "path": "/", "caption": "메인 화면"},
  {"id": 2, "action": "click", "selector": "text=검색", "caption": "검색 기능"},
  {"id": 3, "action": "type", "selector": "input[name=q]", "value": "React", "caption": "키워드 입력"}
]}
```

capture.json — B가 만들어 A에게 넘긴다.

```json
{"viewport": {"w": 1280, "h": 720}, "shots": [
  {"stepId": 1, "image": "shots/1.png", "click": null},
  {"stepId": 2, "image": "shots/2.png", "click": {"x": 640, "y": 120}}
]}
```

scene.json — A가 만들어 B(렌더링)와 C(미리보기·수정)가 쓴다.

```json
{"fps": 30, "totalSec": 60, "scenes": [
  {"type": "title", "durationSec": 3, "text": "프로젝트명"},
  {"type": "screen", "durationSec": 6, "image": "shots/2.png", "zoom": {"x": 640, "y": 120, "scale": 1.6}, "cursor": {"x": 640, "y": 120}, "caption": "검색 기능"},
  {"type": "architecture", "durationSec": 6, "nodes": ["Next.js", "FastAPI", "PostgreSQL"], "edges": [[0, 1], [1, 2]]}
]}
```

## 발표 전략과 시연 시나리오

발표의 핵심 장치는 "지금 보신 발표 영상도 DemoDay로 만들었습니다"라는 반전이다.

1. **오프닝 (30초):** 데모영상을 찍다 버그가 나서 다시 찍었던 경험 등 팀이 직접 겪은 문제로 시작한다.
2. **서비스 소개 영상 (60\~90초):** DemoDay 자체의 레포를 넣어 만든 데모 영상을 튼다. 아키텍처 장면까지 포함한다.
3. **반전 공개:** 방금 영상이 서비스 결과물이라고 밝히고, 사람이 손댄 부분이 없다는 점을 강조한다.
4. **라이브 시연 (1\~2분):** 심사위원 앞에서 다른 샘플 레포를 넣고 시나리오 추출과 미리보기까지 보여준다. 렌더링 시간이 길면 사전 렌더링본과 병행한다.
5. **차별점 정리:** 코드 기반, 실제 화면, 개발 맥락, 발표 맞춤 네 가지를 비교표로 보여준다.
6. **향후 계획:** 요청 흐름·ERD 애니메이션, 모바일 앱 지원, 학과 프로젝트 아카이브 연계를 짧게 언급한다.

예상 질문과 답변을 미리 준비한다.

- **"그냥 ChatGPT나 Claude로 하면 되지 않나요?"** 범용 AI는 실제 화면을 모르고, 코드를 읽어 시나리오를 짜지 않으며, 부분 수정이 어렵다고 답한다.
- **"모션그래픽은 결국 포장 아닌가요?"** 모든 장면이 실제 배포 서비스를 조작한 캡처라는 점을 근거로 답한다.
- **"컴퓨터학부 특화인가요?"** 입력이 코드 레포이고 아키텍처·API 흐름 장면을 만든다는 점을 강조한다.

## 리스크와 대응

가장 큰 리스크는 다양한 레포 구조에 대한 분석 실패와, 라이브 시연 중 렌더링 지연이다.

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 레포 구조가 제각각이라 라우트 추출 실패 | 시나리오가 엉뚱하게 나옴 | MVP는 React/Next.js로 한정, 실패 시 사용자가 장면을 직접 추가하는 폴백 제공 |
| 헤드리스 캡처 중 클릭 대상 못 찾음 | 장면 누락 | 실패한 단계는 정적 스크린샷 장면으로 대체 |
| 로그인·결제 등 인증이 필요한 페이지 | 캡처 불가 | 테스트 계정 입력, MVP는 비로그인 페이지 우선 |
| 영상 렌더링 시간이 김 | 라이브 시연 지연 | 짧은 미리보기 해상도로 먼저 보여주고, 최종본은 사전 렌더링 |
| LLM 호출 비용·속도 | 시연 중 지연 | 분석 결과 캐싱, 샘플 레포는 미리 분석해 둠 |
| 비공개 레포·민감 정보 노출 | 보안 우려 | 공개 레포만 지원하고, 캡처 화면의 입력값은 마스킹 |

## 향후 확장 계획

해커톤 이후에는 개발 맥락 장면을 늘리고, 학과 단위 서비스로 넓히는 방향으로 확장한다.

- **개발 맥락 장면 확대:** API 요청 흐름, ERD, 배포 파이프라인 애니메이션을 추가한다.
- **지원 범위 확대:** Spring Boot, FastAPI 같은 백엔드 중심 프로젝트, 모바일 앱(에뮬레이터 캡처), CLI 도구를 지원한다.
- **자연어 편집:** "두 번째 장면을 더 빠르게", "검색 기능을 강조해줘" 같은 요청으로 수정한다.
- **발표 패키지:** 데모 영상과 함께 발표 슬라이드 초안, 대본, README용 GIF를 한 번에 만든다.
- **학과 아카이브 연계:** 캡스톤·해커톤 결과물을 데모 영상과 함께 모아 보는 학과 프로젝트 갤러리로 발전시켜, 후배들이 선배 프로젝트를 참고할 수 있게 한다.
